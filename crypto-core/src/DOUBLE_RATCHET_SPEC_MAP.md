# Vardum Double Ratchet — Signal spec conformance map (`veil-ratchet-6`, b56)

This document maps the engine (`vendor/crypto-core/src/ratchet.ts`, protocol
tag `veil-ratchet-6`, constants in `constants.ts`) to the Signal Double
Ratchet specification (rev. 4) and states where Vardum deviates. b54 (Batch A)
moved every DH to X25519, made post-quantum mandatory and switched ratchet
signing on. `veil-ratchet-6` (Batch C step 2, Batch D D-12) renamed every
label `-5` → `-6`, added the `DH(EK, IK_responder)` term to contact sessions,
split ratchet signing into one key pair per direction, bound the responder's
first ratchet key and the session dials into both fingerprints, and moved the
header signature check ahead of any chain work. The ratchet structure itself
is unchanged from b185. The wire-level description is
`docs/audit/package/04-protocol-spec.md` §3–§4.

Signal publishes no official test-vector file for the Double Ratchet. The
acceptance bar is therefore **(a)** the frozen self-published deterministic
vector suite (`repro/vectors/dr2_vectors.json`, suite `vardum-dr-vectors-2`,
regenerated for `veil-ratchet-6`; generated by `repro/gen_dr_vectors.ts`,
verified by `repro/b185_dr_vectors.test.ts`) and **(b)** the conformance
assertions below. Any byte-level engine change must fail the suite.

## Deviations (all deliberate, all documented)

1. **PQ-extended KDF_RK.** Every DH step mixes ML-KEM secrets into
   KDF_RK: the receiver decapsulates the sender's `pqct` (encapsulated to the
   receiver's current step key) into `rootA`, and encapsulates to the
   sender's step key `pq` for `rootB`; its ciphertext travels as `pqct` in
   the receiver's next headers (re-sent until its next DH step). Each side
   generates a fresh ML-KEM-768 step keypair at every step. In
   `veil-ratchet-6` this is **mandatory**: a DH step whose header lacks a
   well-formed `pq` is rejected, and a key-generation failure aborts. The
   first headers after the handshake carry `pq` but no `pqct` (no step key of
   the peer is known yet), so the first DH step mixes in only `pqAnswer`.

2. **Session establishment** is Vardum's invite / contact handshake rather
   than X3DH:
   - invite: `shared = DH(hs_R, HS_I) ‖ ML-KEM ss ‖ pp`, where
     `pp = HKDF(k, salt = "vardum-pp-6:" ‖ token, info = "pp")` and `k` is a
     link secret that never reaches the relay; a transcript fingerprint over
     every public handshake value, the responder's first ratchet key, the
     dials and `SHA-256(shared)` is compared by the users;
   - one-tap contact: `shared = DH(ek, SPK) ‖ DH(ek, IK_responder) ‖ ML-KEM ss`,
     with the IK-signed SPK, the IK-signed ML-KEM prekey and the responder's
     **pinned** Ed25519 identity key converted to X25519 (as X3DH's
     `DH(EK_A, IK_B)`); the request `{v:3, t, ek, to, pq, spk, d}` is signed
     by the initiator's IK and carries the canonical dials `d`.
   There is no initiator-identity DH term (X3DH's `DH(IK_A, SPK_B)`): the
   initiator is authenticated by its IK signature over the request, checked
   against the responder's pin. No one-time prekeys (OPKs): disclosed,
   roadmap.

3. **Signed ratchet keys, one key pair per direction.**
   `sigSeed_d = HKDF(rk0, salt = "vardum-ratchet-sig-6:" ‖ token,
   info = "vardum-ratchet-sig-6/" ‖ d)` for `d ∈ {initiator, responder}`.
   Each side signs with its own direction's key and verifies with the peer's,
   so a header can't be reflected back. Every header carries
   `Ed25519(sigPriv, "vardum-ratchet-sig-6:" ‖ rp ‖ ":" ‖ pq)` (b64 text).
   A header that introduces a new `rp` is verified **before any chain work**
   (before the old chain is drained to `pn`; D-12, RV-21); unsigned or
   invalid → rejected with no state change. Headers on an existing chain are
   authenticated by the AEAD. Defence in depth: both pairs derive from `rk0`,
   and the root salt already makes an injected `rp` non-exploitable.

4. **Epoch replay guard** (`seenRemotePubs`, last 64): a header replaying an
   already-replaced remote pub is rejected outright.

5. **Own-echo guard** (`myPubs`, last 64): an envelope carrying one of this
   side's own ratchet pubs is ignored without touching state.

6. **Envelope replay guard** (`processedIds`): idempotent delivery of a
   duplicated envelope id.

7. **Hard cut.** Only `veil-ratchet-6` is accepted (`RATCHET_PROTOCOL_SUPPORTED`).
   A stored state whose `proto` differs, or that isn't hybrid, throws
   `LegacySessionError` on load and the app ends that chat.

Audit posture: the ratchet step, chain advancement, skipped-key handling and
desync guards are spec Double Ratchet over X25519; the PQ extension, the
signed headers and the handshakes are the product-specific elements and are
specified in `docs/audit/package/04-protocol-spec.md` §3–§4.

## Vector suite contents (`dr2_vectors.json`, suite `vardum-dr-vectors-2`)

- KDF_CK / KDF_RK / PQ-mixed KDF_RK known-answers (fixed inputs → fixed bytes)
- ML-KEM-768 encap/decap known-answer (the fixture ships a throwaway keypair)
- 12-op snapshot-chain transcript: ordered sends, reply rotations, held
  out-of-order delivery, duplicate/replay, replayed link by link with
  byte-for-byte equality on every deterministic field
- Cross-epoch straggler scenario (the b185 fix): an E2 envelope delivered
  before an E1 straggler still decrypts via the `header.pn` skip
- Fail-closed: unknown protocol tag rejected with no state damage; counter
  rewind/overshoot rejected

Adversarial coverage lives beside it: `repro/b54_batch_a.test.ts` (one test
per Batch A finding), `repro/batch_c_protocol.test.ts` (B9 IK term and
per-direction keys, NF-7/V-12 fingerprint and dials), `repro/batch_d_d3.test.ts`
(D-12: a forged rotation is refused on its signature before any chain work) and
`repro/b197_stress.test.ts` (200-message soak, 50-header splice flood,
corruption fuzz, replay flood, counter-gap, own-echo).
